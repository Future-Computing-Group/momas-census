# Codebook v2

v1 changes from the v0 pilot (2026-11-06): PRINCIPALS split into INTERESTS (what the problem models) and OWNERS (who controls the decision-makers), because v0 coded self-play games as multi-principal; AGENT tightened to multi-step action.

v2 changes (2026-11-06, after the v1 two-coder pilot, where all ten INTERESTS/OWNERS disagreements were this convention): a paper in which one developer trains or runs one model is the default ML setting and is coded interests=one, owners=one, control=central, boundary=no, whether or not it is an agent paper; NA is reserved for papers with no learner, decision-maker or analyst (e.g. a pure hypothesis test). Running independently developed models side by side in one evaluation or tournament is owners=one (one party deploys them all); human participants acting for themselves are owners=several.

Clarification (2026-11-06, from the author's adjudication of one paper; no other code changes): when the other parties in the setting are generated by the developer (simulated, self-played, or played by one model that represents every side), OWNERS is one; when the method is analysed against parties who choose their own responses (for example applicants who best-respond to a published classifier), OWNERS is several.

Code each paper from its title and abstract only. Code the setting the paper's method or analysis assumes, not settings it mentions in passing (an example task, a motivation sentence). Use NA when the abstract does not fix the dimension.

AGENT: yes if the paper's subject is one or more decision-makers that act over several steps in an environment (RL agents, LLM agents that call tools or act on the web or in software, robots, bidders, players); no if an agent appears only as a component used to build a dataset or as a one-shot LLM call.

DATA: pooled (one dataset under one controller) / partitioned (several owners hold data they do not pool, e.g. federated or cross-silo) / NA.

OBJECTIVE: single (one loss, reward or utility, including a team reward shared by several agents or a min-max game internal to one learner) / multiple (decision-makers have their own, possibly conflicting objectives) / NA.

CONTROL: central (one party designs, trains or orchestrates every decision-maker, even if computation or data is distributed; a federated server counts as central) / decentralized (no single party controls every decision-maker) / NA.

INTERESTS (whose interests the formal setting models): one / several-aligned (several parties with identical or shared goals) / several-conflicting (parties with distinct, possibly opposed goals: game opponents, bidders, negotiators, competing firms) / adversarial (an attacker or threat model against one protected party) / NA.

OWNERS (how many independent parties own or control the decision-makers in the setting): one (a single developer, operator or trainer controls all of them, including self-play and simulated opponents) / several (decision-makers or data owners belong to different organizations or individuals, e.g. federated clients, independently developed agents, human participants acting for themselves, an external attacker) / NA.

BOUNDARY: yes if decision-makers or data owners on different sides of an ownership line interact in the setting; no otherwise.

Output one JSON object per paper: {"id", "agent", "data", "objective", "control", "interests", "owners", "boundary", "confidence" (high/medium/low), "note" (one short sentence quoting the abstract phrase that decided OWNERS)}.
